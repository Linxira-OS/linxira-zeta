# Zeta 1.2.0 执行计划

本计划是 1.2.0 的唯一执行规范：每个工作项都写明了目标、精确改动位置、**已经定下的决策**（实施者不需要再选）与验收方式。范围由用户逐项勾选（见文末「范围决定记录」），接缝由五份只读侦察（`TrackRecon` / `MemRecon` / `TeamRecon` / `WebSdkRecon` / `CmdRecon`，基于 main `0d14e12cc30`）逐条取证。

**时序策略（用户定，本轮窗口专用）**：1.2.0 发布失败 → 上游合并随修复合入同一次发布；1.2.0 正常发布 → **当日**再发 1.2.1 带走上游合并。上游并入一律真 tag 双父合并（非 squash、非 cherry-pick），tag 由用户点名（建议在真正开始合并时取当时最新的已核实 tag）。

**通用门禁**（每个工作项合并前必须过）：`bun scripts/brand/brand-check.ts` 归零、`bun scripts/check-zeta-sentinels.ts` 归零、`bun x oxfmt --check` 对改动的 TS 归零、`bun run check:ts` 零错误；动过 crates/ 加 `cargo fmt --all --check`；新增 Zeta-only 行为必须同步 `scripts/brand/zeta-sentinels.ts`。PR 绿不等于真绿——每个合并都在 main 的 push run 上复核，且**必须核对 jobs 数**（单 job 的 `Zeta Nix` run 不是主流水线）。

## 3. M3a — 内存压力卸载 · 分支 `feat/memory-pressure-shed`

**目标**：内存紧张时主动降级，而不是等到崩溃（用户机器真实崩过，os error 1455）。

**机制修正（侦察证伪原设想）**：仓库里**没有**推送式内存压力事件（roadmap 写的 `process.on("memoryPressure")` 零引用）。`task/fanout-pressure.ts` 是纯拉取采样器（`readMemorySample()`/`memoryPressureLevel()`，TIGHT/CRITICAL 阈值），只在两个决策点被调用。因此本项做成**在既有检查点拉取并按级卸载**。

**改动**
1. 检查点：沿用 `task/index.ts:793-800`（spawn 许可）与 `task/workpool.ts:157-161`（workpool 上限）的采样；在 **turn_end** 增加一次（先例：`agent-session.ts:6191-6227` 的 `#settleOwnedBrowserTabs`）。
2. 卸载序列（按代价从低到高，全部走现成 API）：
   - ① TUI 渲染缓存：`clearRenderCache()`（`tui/src/chat/markdown.ts:1291-1294`）+ `clearMermaidCache()`（`tui/src/theme/mermaid-cache.ts:158-160`）——两者已在主题切换时成对调用，直接复用；
   - ② 浏览器空闲 tab：`releaseIdleTabsForOwner(ownerId, { idleMs: 0 })`（`tools/browser/tab-supervisor.ts:1461-1503`，门是 `isIdleCloseCandidate`）；
   - ③ mnemopi 嵌入 worker：`mnemopiEmbedClient.terminate()`（`mnemopi/embed-client.ts:196-213`）——重启代价高，**仅 CRITICAL 级**触发；
   - ④ broker 空闲守护进程：PR #96 的 `#stopUnownedOneShotDaemons` 是私有且受存在性门控，不能被会话驱动——需要新 RPC op 或客户端 `listServices`/`stopService`（`launch/services.ts:123-126,270-273`）。
3. 分级决策：TIGHT → ①②；CRITICAL → ①②③④。每次卸载写一条日志（级别、释放对象、原因），不写 tracking（避免噪声）。

**验收**：真跑——构造 TIGHT/CRITICAL 注入，观察各级卸载发生且不误杀 active tab（`isIdleCloseCandidate` 门生效）；正常内存下不发生任何卸载。

## 5. D4 — web-ui 的 ```svg 渲染 · 分支 `feat/web-svg-fences`

**目标**：web 会话能画提示词里承诺的 ```svg 图。

**关键缝隙（侦察取证）**：`renderSvg`/`renderMermaid` 被 `tuiTranscript` 门控（`sdk.ts:3988-3991`，只有交互式 TUI 置真），所以 **web 会话根本不知道 svg 存在**；模板分支本身**已经存在**（`prompts/system/system-prompt.md:20-28`）。

**改动**
1. **prompt 侧**：在 `CreateAgentSessionOptions` 加一个不可变布尔（与 `renderSvg`/`renderMermaid` 并列消费于 `sdk.ts:3988-3991`），由 serve / web-gateway 的建会话路径置真。**不得**做成 settings 读取（会话期不可变是既有契约）。
2. **渲染侧**：`web-ui/components/MarkdownBody.tsx:41-53` 增加 `lang === "svg"` 分支 → 新组件 `SvgBlock`，照 `MermaidBlock.tsx` 的既有形态（源码/预览切换、CodeBlock 回退、放大对话框）。
3. **sanitize 决策**：现有管线是 react-markdown + rehype-raw + rehype-sanitize（默认 schema 会剥掉内联 svg）。采用 **DOMPurify**（目前只是 mermaid 的传递依赖，需提为直接依赖）对 svg 子集消毒后再注入，允许面仅限提示词承诺的静态图形（禁 script / foreignObject / 外部 href / 事件属性）。
4. **颜色**：提示词承诺 `currentColor` 与 `var(--fg|--muted|--border|--surface|--accent|--success|--warning|--error|--c1..--c6)`，web-ui 侧没有这些名字——在 `globals.css` 加一层 token 别名映射到既有变量（`--text`/`--text-muted`/`--bg-panel`/`--status-*`/`--chart-*`），并注意 `--muted` 在 web-ui 已另有含义（surface-muted），别名要用作用域包住。
5. **流式**：只渲染**已闭合**的围栏（TUI 的 `closePartialSvg` 在 `packages/tui`，不可导入；web 侧无需复刻增量渲染）。

**验收**：浏览器里真渲染一条含 ```svg 的消息（视觉确认）；恶意样例（script、foreignObject、外链、事件属性）全部被剥离；在无别名变量缺失时不崩；流式过程中未闭合围栏按代码块显示。

## 7. D8b — 自定义命令热重载 · 分支 `feat/command-hot-reload`

**目标**：改一个 TS 自定义命令文件，无需重开会话即可生效。

**事实（侦察取证）**：今天没有任何东西重载 TS 自定义命令（只有会话构造时加载，`sdk.ts:1862-1865`）；`/reload-plugins` 只覆盖技能 + markdown 命令 + MCP。settings 的目录 watcher（`config/settings.ts:1205-1211`，200 ms 防抖）是可复用的**范式**，但它是 Settings 私有的且只盯配置文件。

**改动**
1. 新增一个盯自定义命令目录的 watcher（照 settings 的 `fs.watch` + 防抖 + keep-last-good 结构）。
2. 失效面：刷新 `AgentSession.#customCommands`（`agent-session.ts:1139,2385`）并调用 `#notifyCommandMetadataChanged`（`5916-5931`）——TUI（2470）、ACP（2125）、RPC（1747）三处订阅者随之刷新。
3. 缓存击穿：`extensibility/custom-commands/loader.ts:41` 是裸 `await import`，需要 query-string 破缓存；注意 Windows 的已记录坑（`docs/extension-loading.md:279`）。
4. 决策：监视深度 = 每个命令目录的 depth-1 `index.*`；防抖 200 ms；解析失败 = 保留上一个好版本 + 一条可见警告（不崩会话）。

**验收**：编辑一个命令文件后，TUI/ACP/RPC 三处的命令描述都刷新；写入坏文件不崩且给出警告；连续快速改动只触发一次重载。

## 8. 机制三项 + lint + roadmap 分类修正 · 分支 `chore/tools-and-lint`

1. **`scripts/watch-ci.ts <sha>`**：等 CI 的规范工具。语义照 `scripts/release.ts` 的 `watchCI`——**盯该 commit 的全部 run，只有所有 run 都 completed 且无失败才算绿**（单 job 的 `Zeta Nix` run 因此不能让它提前判绿）；但接受显式 SHA（`watchCI` 硬编码 `HEAD`）。
2. **修 `scripts/merge-scope-report.ts`**：它用裸 `main` 引用（`git diff <sha> main`），而本仓库 `main` 既是分支名又是工作台目录，git 判歧义直接失败——改成 `refs/heads/main`。
3. **manifest 合并驱动器注册写进文档**：`.gitattributes` 绑定了 `package.json` 的 `merge=zeta-package`，但**驱动定义在本机 git config**（还带绝对路径）。在 `document/merge-playbook.md` 的合并前置检查里写明：开始合并前必须在工作 worktree 里注册 `git config merge.zeta-package.driver "bun <repo>/scripts/merge-package-json.ts %A %O %B"`，否则 13 个 manifest 会退化成手工冲突。
4. **lint 清理**：删 `desktop/src/main.ts:400` 未使用的 `bundledServeCommand`；`packages/coding-agent/src/task/parallel.ts:36,108` 与 `packages/natives/bench/text.ts:83` 的 `new Array(n)` 改合规写法。
5. **roadmap 分类修正**：把 `/recipe` 从「OpenCode 官方命令移植」段移除——`recipe` 是上游 OMP 的 **tool**（上游提交 `dfa6007f36b` 已删除），OpenCode 从未有过该命令；它只应留在 P3「已移除工具」清单里。

**验收**：`bun scripts/brand/brand-check.ts`、`check-zeta-sentinels.ts`、`check:tools` 全绿；`watch-ci.ts` 对一个已知绿的 SHA 返回绿、对一个含失败 job 的 SHA 返回红。
